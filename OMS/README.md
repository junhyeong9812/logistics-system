# OMS System

> 스택 가정: Spring Boot(Kotlin) + JPA, PostgreSQL. 이 문서는 도메인 이해용 정리이고, 구현 설계는 아직 아니다.

## 1. 역할

OMS(Order Management System)는 **주문의 정본(source of truth)**이다. 여러 채널에서 들어온 주문을 하나의 표준 주문으로 만들고, "이 주문을 어느 창고에서 어떻게 내보낼지"를 결정한 뒤, 주문이 끝날 때까지 상태를 책임진다.

| OMS가 하는 것 | OMS가 하지 않는 것 (담당 시스템) |
|---|---|
| 채널 주문 수집, 정규화, 검증 | 물리 재고의 입고, 이동, 실사 (WMS) |
| 셀러 룰 적용, 합치기/나누기 | 피킹, 패킹, 출고 확정 (WMS) |
| 창고 할당 결정, 출고 요청 생성 | 운송사 선택, 운송장 발급, 배송 추적 (TMS) |
| 주문 상태 관리, 채널에 결과 회신 | |
| 취소, 변경 접수와 가능 여부 판단 | |

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 채널 | 주문이 들어오는 곳. 쇼핑몰, 마켓플레이스, 자사몰 등 |
| 셀러 (화주) | 물건 주인. 물류사 입장에서는 고객사. 모든 데이터의 소유 단위 |
| 외부 주문번호 | 채널이 매긴 주문번호. `(채널, 셀러, 외부 주문번호)`가 멱등 키 |
| 원문 주문 | 채널이 보낸 그대로의 데이터. 정규화 전 |
| 주문 / 주문 품목 | 정규화된 표준 주문과 그 품목 줄 |
| SKU 매핑 | 채널 상품(옵션) -> 셀러 SKU 변환. 세트 상품은 SKU 여러 개로 풀림 |
| 출고 요청 (Fulfillment Order) | 주문을 창고 단위로 나눈 것. **WMS로 넘기는 문서** |
| 보류 (Hold) | 자동 처리 불가. 사람이 확인해야 함 (주소 오류, 통관 정보 누락 등) |
| 백오더 | 재고가 없어 나중에 내보낼 주문 |

## 3. 주요 프로세스

```text
(P1) 수집 -> (P2) 정규화 -> (P3) 검증, 룰 -> (P4) 합치기/나누기 -> (P4.5) 사은품 결정 -> (P5) 창고 할당 -> (P6) 출고 요청 전달 --> [WMS]
                                  |                                                              |
                                  +--> 보류 (사람 확인)                                            +--> 백오더
[WMS], [TMS] 이벤트 --> (P7) 상태 반영 --> 채널에 송장, 상태 회신
(P8) 취소, 변경: 어느 단계에서든 들어올 수 있음
```

| 프로세스 | 입력 | 출력 | 실패하면 |
|---|---|---|---|
| P1 수집 | webhook 또는 polling 결과 | 원문 주문 저장 | 재수신으로 복구. 유실이 최악 |
| P2 정규화 | 원문 주문 | 표준 주문 (SKU 매핑, 주소, 통화) | 매핑 실패 -> 보류 |
| P3 검증, 룰 | 표준 주문 | 통과 / 보류 / 룰 적용된 주문 | 보류 |
| P4 합치기/나누기 | 같은 수취인 주문들, 품목 | 합포장 묶음 또는 분할 단위 | - |
| P4.5 사은품 결정 | 주문, 사은품 정책 | 사은품 품목이 추가된 주문 | 사은품 재고 없음 -> 정책에 따라 빼고 진행 / 보류 |
| P5 창고 할당 | 주문(본품 + 사은품) + 창고별 가용 재고 | 창고별 출고 요청 | 재고 부족 -> 분할, 백오더 |
| P6 출고 요청 전달 | 출고 요청 | WMS 수신 확인 | 재시도 (같은 요청 ID) |
| P7 상태 반영 | WMS, TMS 이벤트 | 주문 상태 갱신, 채널 회신 | 순서 뒤집힘은 전이 규칙으로 무시 |
| P8 취소, 변경 | 채널 또는 셀러 요청 | 단계별 취소 처리 | 이미 출고됨 -> 반품 흐름으로 |

### 프로세스별 메모

- **P1 수집**: 원문을 먼저 저장하고 응답한다. 정규화는 비동기로 한다. 같은 주문이 webhook 재전송, polling 겹침으로 여러 번 오는 것이 정상이다.
- **P2 정규화**: 채널마다 형식이 다른 것을 흡수하는 곳이라 채널별 어댑터가 생긴다. 크로스보더라 통화, 국가 코드, 현지어 주소가 섞인다.
- **P3 검증, 룰**: 해외 배송이라 통관 정보(HS 코드, 신고 가격, 품목명 영문)가 필수다. [추정] 셀러 룰 예: 사은품 추가, 특정 SKU 보류, 금액 기준 운송 서비스 지정.
- **P4.5 사은품 결정**: 수집과 떼어낸 후처리 단계다. 사은품은 실물 SKU라 재고 할당, 피킹, 패킹 대상이므로 할당 전에 끝나야 한다(TMS 단계에서는 박스가 이미 닫혀 있다). 순서의 근거는 큐 순서가 아니라 주문에 저장한 채널 결제 시각(`paid_at`)이다. 6.2의 11번.
- **P5 창고 할당**: 재고의 정본은 WMS다. OMS는 할당 판단에 쓸 가용 재고를 어디서 보는가가 쟁점이다 (6.2의 15번).
- **P8 취소**: 취소는 상태에 따라 비용이 다르다. 할당 전 = 상태만 변경, 피킹 전 = 출고 요청 취소, 운송장 발급 후 = 운송장 취소, 출고 후 = 취소 불가(반품).

## 4. 주문 상태 (초안)

```text
수신 -> 정규화됨 -> 검증됨 -> 할당됨 -> 출고 요청됨 -> 출고 완료 -> 배송 중 -> 배송 완료
          |           |         |
          +-> 보류 <---+         +-> 백오더
어느 단계든 -> 취소 요청 -> 취소됨 / 취소 불가
```

- 할당됨 이후의 상태는 OMS가 스스로 바꾸지 않는다. WMS, TMS 이벤트를 받아 바뀐다.
- 주문 하나가 출고 요청 여러 개로 나뉘면 "일부 출고"가 생긴다. 주문 상태를 출고 요청 상태들의 집계로 볼지 정해야 한다.

## 5. 다른 시스템과 주고받는 것

| 방향 | 내용 |
|---|---|
| OMS -> WMS | 출고 요청 생성, 출고 요청 취소 |
| WMS -> OMS | 출고 요청 접수됨 / 재고 부족 / 피킹 시작 / 출고 확정, 가용 재고 변동 |
| TMS -> OMS | 운송장 발급됨 (운송장 번호), 배송 상태 변경 |
| OMS -> 채널 | 송장 번호 회신, 취소 결과 |

## 6. 쟁점

### 6.1 전제: 데이터 특성

쟁점은 아래 특성을 놓고 판단한다. 숫자는 루트 README 4절 기준이다. 이 OMS는 풀필먼트 OMS로 본다(`docs/scope.md` 1절). 가격, 할인, 등급 계산은 범위 밖이다.

| 특성 | 값 | 주로 영향받는 쟁점 |
|---|---|---|
| 평시 유입 | 하루 50만 건, 초당 약 6건 | 1(보관량) |
| 이벤트 순간 최고치 | 300만 건이 1시간~10분에 몰림, 초당 830~5,000건 | 2, 4, 18 |
| 누적량 | 주문 연 약 1.8억 행, 품목은 그 몇 배 [가정 수치] | 1(파티셔닝, 보관) |
| 셀러 쏠림 | 대형 셀러 한 곳이 이벤트로 100만 건 | 2(공정성), 1(파티션 키) |
| 핫 SKU | 같은 SKU에 동시 할당 수천~1만 건 | 15, 11(선착순 사은품) |
| 중복 수신 | webhook 재전송, polling 겹침, 큐 최소 1회 전달 | 1(멱등 키), 4 |

### 6.2 쟁점 목록

앞 번호의 결정이 뒤 번호의 전제가 되는 순서다. 결정되면 "결정"에 적는다.

| # | 쟁점 | ERD에 미치는 영향 | 선택지 | 결정 |
|---|---|---|---|---|
| 1 | 식별자, 테넌트, 파티션 키 | 모든 테이블의 PK, `seller_id` 위치, unique 제약, 파티션 단위 | 내부 ID: Long 시퀀스 / UUID v4 / UUID v7(ULID). 파티션: 없음 / 시간 범위 / 셀러 해시. 멱등 키를 주문 테이블에 둘지 별도 테이블로 둘지 | PK = UUID v7, 파티션 키 = `id`(월 단위 범위 파티션, 실험에 실제 적용). 멱등 키 = 파티션하지 않은 별도 테이블 `order_idempotency_key(channel_id, seller_id, external_order_no) -> order_id`. `seller_id` = 하위 테이블까지 전부. 사람이 읽는 주문번호 = 별도 컬럼(시퀀스) |
| 2 | 수집 경로와 큐 | 원문 저장 시점, 큐에 무엇을 싣는가 | 원문 저장 후 응답 -> 큐. 표준 큐 / FIFO(그룹 = 셀러). 셀러 공정성: 큐 분리 / 컨슈머 쪽 셀러별 처리량 상한 | 원문 저장 후 200 응답(정규화는 비동기). 원문 저장 + 발행 내용을 같은 트랜잭션에 기록(outbox). 큐 = 표준 큐(순서 불필요, 중복은 1번의 멱등 키 제약이 막음). 셀러 공정성 = 큐 하나 + 컨슈머 쪽 셀러별 처리량 상한, ADR 3 측정 후 재검토. 원문 저장 위치는 3번 |
| 3 | 원문 주문과 표준 주문 분리 | 원문 테이블 유무, 저장 형태 | 원문 = PostgreSQL `jsonb` / S3 + 참조 키. 표준 주문과 1:1 또는 1:N(수정본) | 원문 = PostgreSQL `jsonb`, 월 단위 범위 파티션, 보관 3개월 후 S3로 이동. 원문 N : 주문 1, 내용이 바뀐 수정본만 새 버전으로 쌓음. S3 이관본은 4번 (d)대로 암호화 |
| 4 | 재수신, 수정본 처리 | 원문 버전, 주문 갱신 규칙, 동시 수신 처리 | 무시(최초만) / 새 버전으로 갱신(단계 제한) / 보류. 동시 수신: unique 제약 + `ON CONFLICT` / 선조회 후 삽입 | 수집 시 `order_id`(UUID v7) 1회 발급. 멱등 키 테이블에 `payload_hash`, `channel_updated_at` 추가, `INSERT ... ON CONFLICT`로 판정 (처음 = 원문 저장 + 발행 / 해시 같음 = 저장 없이 200 / 해시 다름 = 수정본). 원문 저장, 판정, outbox 기록은 한 트랜잭션. `channel_updated_at`이 더 오래된 수정본은 원문만 남기고 반영 안 함. 수정본 처리: 할당 전 = 교체 후 재처리 / 할당 후 출고 요청 전 = 변경 요청(17번) / 출고 요청 후 = 보류 보완: (a) `payload_hash`는 정규화에 쓰는 필드(품목, 수량, 주소, 금액, 상태)만으로 계산, 필드 목록은 채널 어댑터별. (b) `channel_updated_at`을 안 주는 채널은 들어온 순서대로 반영. (c) 멱등 키 테이블 보관 = 최소 1년 또는 채널 재전송 가능 기간 이상. (d) 원문 개인정보 = 복호화 가능한 암호화(AES-256-GCM, 키는 KMS 봉투 암호화)로 S3 보관 |
| 5 | 주문 애그리거트 경계 | 주문, 품목, 수취인, 금액이 한 애그리거트인가, 버전 컬럼 | 주문 루트 + 품목, 수취인 내부 엔티티 / 품목 분리. 낙관적 락 `version` | 루트 `orders`(헤더, 상태, `version`) + 내부 `order_line`(PK `(order_id, line_no)`, 사은품 여부와 `promotion_id`) + 내부 `order_recipient`(PK `order_id`, 1:1, 테이블만 분리). 세 테이블 모두 `order_id` 월 범위 파티션. 수취인 이름, 연락처, 주소 = 복호화 가능한 암호화(`bytea`), 검색 필드는 HMAC 컬럼 + 인덱스. 동시 수정 = 루트 `@Version` 낙관적 락, 품목 변경도 루트를 거쳐 version 증가, 충돌 시 다시 읽고 규칙 재적용. 출고 요청, 보류, 상태 이력은 애그리거트 밖(ID 참조). B2B 대량 주문은 범위 밖 |
| 6 | 상품, SKU 마스터 소유 | SKU 테이블이 OMS에 있는가, 세트 상품 분해 테이블 | OMS가 상품 매핑 소유 + SKU는 WMS 정본의 사본 / 공통 상품 마스터 | 상품 마스터는 별도 PMS(Product Management System)가 정본. 채널 상품 매핑, 세트 구성, 실측 무게와 크기(WMS가 재서 PMS에 이벤트로 반영)도 PMS 소유. OMS, WMS, TMS는 ID만 참조 |
| 7 | 주문 시점 값 스냅샷 | 품목에 상품명, 가격(할인 반영 후), HS 코드, 신고가, 등급 플래그를 복사하는가 | 스냅샷 복사 / 마스터 참조 | 마스터 값은 복사하지 않고 `(sku_id, sku_version)` 버전 참조. PMS는 수정 시 새 버전을 만들고 기존 버전은 불변. 단가(할인 반영 후), 통화, 수량은 채널 주문 데이터라 `order_line`에 직접 저장. 세트는 구성품으로 나누는 것이 기본, 세트 가격은 구성품 신고가 비율로 배분(통관, 정산 단위 = 구성품 HS 코드) |
