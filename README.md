# 물류시스템 - OMS, WMS, TMS 설계 실험

> 시작: 2026-10-29. 기한 없음 — 전체 그림을 먼저 그리는 것이 목적이다.

## 1. 왜 이 주제인가

문제 설정:
- 다양한 채널의 주문을 어떻게 처리할지, 창고 관리, 배차, 물류 시스템 전반을 설계한다.
- 하루 수십만 건이 처리되고, 이벤트 때는 주문이 한 번에 수백만 건 몰리며, 해외로 나간다.
- 서버를 어떻게 나눌지가 핵심 쟁점이다.

가정 스택:
- BE: Express, Nest, Spring(Kotlin)
- 저장소: PostgreSQL, DynamoDB, Redis, OpenSearch
- AWS: Lambda, EventBridge, SQS, SES, ECS, S3
- 아키텍처: MSA, EDA, Layered, Hexagonal, TDD, DDD

목적은 완성품이 아니라 **설계 쟁점을 손으로 한 번 겪고, 직접 잰 숫자를 남기는 것**이다.

## 2. 세 시스템

| 이름 | 하는 일 | 핵심 데이터 |
|---|---|---|
| OMS (Order Management System, 주문 관리) | 채널별 주문 수집, 정규화, 검증, 합치기/나누기, 룰 적용, 주문 상태 관리, 창고 할당 결정 | 주문, 주문 품목, 셀러, 채널, 룰 |
| WMS (Warehouse Management System, 창고 관리) | 입고(ASN, 검수), 적치(로케이션), 재고(가용/할당/보류), 출고 지시(웨이브), 피킹, 패킹, 출고 확정 | SKU, 로케이션, 재고, 웨이브, 피킹 리스트 |
| TMS (Transportation Management System, 운송 관리) | 운송사, 서비스 선택, 운송장(라벨) 발급, 배차, 출고 마감 시간 관리, 구간별 추적 | 운송사, 운임표, 운송장, 추적 이벤트 |

- MES(제조 실행 시스템)는 공장 공정 관리라 이 주제와 관계없다.
- 택배형 해외 배송에서 "배차"는 차량 배차보다 운송사, 서비스 선택과 출고 마감 시간에 맞춘 묶음 출고에 가깝다. [추정]
- 크로스보더 물류에 대응시키면: 멀티 스토어 통합, 룰 엔진, 사전 검증 = OMS / 해외 창고 연계 = WMS / 다수 운송사 연동, 구간별 추적 = TMS.

## 3. 주문 한 건의 흐름

```text
[쇼핑몰] --webhook/polling--> (1) 수집 --> (2) 정규화, 검증, 룰 --> (3) 창고, 재고 할당     [OMS]
   --> (4) 출고 지시(웨이브) --> (5) 피킹, 패킹 --> 출고 확정                                [WMS]
   --> (6) 운송장 발급 --> (7) 쇼핑몰에 송장 회신 --> (8) 구간별 추적 --> 배송 완료          [TMS]
```

| 단계 | 부하 모양 | 외부 의존 | 실패하면 |
|---|---|---|---|
| (1) 수집 | 이벤트 때 순간 폭주 | 쇼핑몰 API(속도 제한) | 주문 유실 = 최악 |
| (2) 검증, 룰 | CPU, 셀러별 룰 | 없음 | 보류로 빼고 사람이 확인 |
| (3) 할당 | 같은 SKU 동시 접근(핫 SKU) | 없음 | 초과 할당 |
| (4)(5) 창고 | 창고 처리 능력이 상한 | 창고 WMS | 출고 마감 놓침 |
| (6) 운송장 | 느리고 제한 있는 API | 운송사 여러 곳 | 출고 지연 |
| (8) 추적 | 건당 이벤트 여러 개, 꾸준히 많음 | 운송사 webhook/polling | 고객 문의 증가 |

단계마다 부하 모양이 다르다. 이것이 서버를 나누는 근거가 된다.

## 4. 숫자 감각

- 하루 50만 건을 고르게 받으면 50만 / 86,400초 = 초당 약 6건.
- 이벤트 300만 건이 1시간에 몰리면 초당 약 830건, 10분에 몰리면 초당 5,000건.
- 문제는 평균이 아니라 순간 최고치와 뒷단 처리 능력의 차이다. 앞단은 받아서 쌓고, 뒷단은 감당할 속도로 꺼내 간다(큐로 부하 평준화).
- 추적 이벤트: 주문 1건당 5~10개로 가정하면 하루 50만 건 -> 250만~500만 이벤트. [가정 수치]

## 5. 설계 쟁점

1. **폭주 수집**: 원문 먼저 저장 -> 200 응답 -> 큐. 멱등 키 = (채널, 셀러, 외부 주문번호). webhook 재전송, polling 겹침, SQS 중복 전달(표준 큐는 최소 1회 전달)을 같은 키로 막는다.
2. **셀러 공정성**: 대형 셀러 이벤트가 작은 셀러를 막지 않게. 큐 분리 / FIFO message group = 셀러 / 컨슈머 쪽 셀러별 처리량 상한. FIFO 처리량 상한은 AWS 문서로 확인한다. [확인 필요]
3. **재고 할당**: 불변식 = 가용 재고 >= 0. 조건부 UPDATE / 비관적 락 / Redis Lua 선차감 -> DB 확정 / DynamoDB 조건부 쓰기 / 재고 버킷 분할. 할당(예약)과 차감(출고 확정)을 나누고, 취소하면 예약을 되돌린다.
4. **다중 창고 할당**: 가까운 창고 -> 한 창고에서 다 채우기(분할 출고 최소화) -> 분할 -> 백오더. 규칙은 셀러별 룰 엔진.
5. **웨이브 vs 연속 할당**: 웨이브는 단순하지만 대기가 생기고, 연속 할당은 빠르지만 패킹이 새 병목이 된다. 이벤트 때는 웨이브당 피킹 상한을 둔다.
6. **외부 API**: 운송사별 어댑터(Hexagonal 포트/어댑터), 운송사별 처리량 상한, 지수 백오프 + 지터, DLQ, 서킷 브레이커, 대체 운송사, 운송장 발급 멱등 키.
7. **상태와 이벤트**: 주문 상태 머신, Transactional Outbox, 순서 뒤집힌 이벤트는 전이 규칙으로 무시, 출고 직전 취소는 보상 처리(Saga).
8. **서버 분리**: 기준 = 부하 모양, 장애 격리, 외부 의존, 팀 구조.
   - 후보: 수집 / 주문(OMS) / 재고, 할당 / 창고 연동 / 운송(TMS) / 추적 / 조회(OpenSearch, CQRS).
   - 처음엔 모듈 경계만 나누고 큐로 잇는다. 배포 분리는 필요해진 곳(수집, 추적)부터 한다.
   - 데이터는 셀러 ID 파티션 + 대형 셀러용 보조 해시 키로 나눈다.

## 6. 할 일 - 실험 범위 (후보 A 중심)

**A. 주문 폭주 수집 -> 재고 할당 파이프라인** (우선)
- 가짜 쇼핑몰 2곳(webhook형, polling형) -> 수집 API(원문 저장 + SQS) -> 정규화, 멱등 처리 -> 다중 창고 재고 할당 -> outbox로 "할당됨" 이벤트 발행.
- 스택: Kotlin + Spring Boot, PostgreSQL, Redis, LocalStack(SQS, DynamoDB), k6, Docker Compose.
- ADR 질문:
  1. 같은 주문을 3번씩 보내도 유실 0, 중복 0인가
  2. 핫 SKU 하나에 동시 1만 건: 조건부 UPDATE vs Redis 선차감, 초과 할당 0 유지와 처리량
  3. 대형 셀러 100만 건 + 소형 셀러 1,000건: 큐 하나 vs 셀러별 공정 처리에서 소형 셀러 대기 시간

**B. 운송사 연동 게이트웨이** (여유 있으면)
- 가짜 운송사 3곳(느림, 속도 제한, 간헐 장애) -> 어댑터 + 처리량 상한 + 재시도/DLQ + 서킷 브레이커.
- 한 운송사가 죽어도 다른 운송사 출고가 영향받지 않는지, DLQ 재처리.

**C. 미니 WMS 웨이브** (선택)
- 출고 마감 기준 웨이브 묶기, 웨이브당 피킹 상한, 로케이션 기반 피킹 리스트.

결과물: 이 폴더의 README(흐름도, ADR, 측정표). 진행 중인 것은 "진행 중"으로 적는다.

## 7. 진행 순서

기한은 두지 않는다. 진행 단계는 `docs/scope.md` 3절을 따른다.

| 순서 | 할 일 |

| 3 | 구현 실험: 6절 A(수집 -> 할당), B(운송사 게이트웨이), C(웨이브) |

## 8. 설계 질문에 답하는 순서

1. 요구사항 질문: 채널 수, 하루/이벤트 최고 건수, 창고 수, 출고 마감 시간, 허용 지연, 절대 틀리면 안 되는 것(유실? 초과 할당?)
2. 숫자 계산: 초당 건수로 바꾼다
3. 흐름도: 3번의 8단계
4. 저장소와 이유: PostgreSQL(주문, 재고 정합성) / DynamoDB(추적, 멱등 키) / Redis(핫 데이터, 처리량 상한) / OpenSearch(조회) / S3(원문)
5. 실패 시나리오: 중복, 유실, 순서 뒤집힘, 외부 장애, 핫 SKU, 대형 셀러 폭주
6. 트레이드오프: 고른 것, 고르지 않은 것, 이유
7. 관측: 큐 적체(남은 메시지 수, 가장 오래된 메시지 나이), DLQ 건수, 단계별 처리 시간
