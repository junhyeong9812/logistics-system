# PMS System

> 스택 가정: Spring Boot(Kotlin) + JPA, PostgreSQL. OMS 쟁점 6, 7번에서 분리됨. 범위는 `docs/scope.md` 2절 PMS.

## 1. 역할

상품이 무엇인지에 대한 정본. OMS, WMS, TMS는 `(sku_id, sku_version)`만 참조한다(OMS 7).

| 맡는 것 | 쓰는 쪽 |
|---|---|
| SKU 마스터(이름, 셀러 SKU 코드, 바코드) | 전부 |
| 채널 상품 매핑(채널 상품, 옵션 -> SKU 또는 세트) | OMS P2 정규화 |
| 세트 구성(구성품, 수량, 신고가 비율) | OMS P2, 세트 분할(OMS 7) |
| 통관 정보(HS 코드, 영문 품목명, 원산지, 신고가) | OMS P3 검증, TMS 통관 서류 |
| 실측 무게와 크기(WMS가 재서 이벤트로 보냄) | WMS 박스 선정, TMS 운임 |
| 취급 속성(파손 주의, 위험물, 유통기한 관리 여부) | WMS 보관, 피킹 |

## 2. 쟁점

| # | 쟁점 | 핵심 질문 | 결정 |
|---|---|---|---|
| P1 | 상품 식별 | `sku_id` 전역. 셀러 SKU 코드 유일 범위, 바코드 여러 개 허용 여부 | 미정 |
| P2 | 버전 모델 | 어떤 필드 변경이 새 버전을 만드나, 표시용 수정도 버전인가 | 출고, 통관에 영향 주는 필드(무게, 크기, HS 코드, 신고가, 세트 구성, 취급 속성)가 바뀌면 새 버전. 기존 버전은 불변. 표시용 필드(상품명 오타, 설명)는 버전 없이 수정. 테이블 = `sku`(불변 식별, 현재 버전 포인터, 표시용 필드) + `sku_version`(PK `(sku_id, version)`, 버전 대상 필드, 생성 시각, 생성 주체, 원인) + `sku_barcode`. 주문은 수집 시점의 현재 버전을 참조하고 이후 버전을 따라가지 않는다. 예외(신고값과 실측값 차이가 클 때)는 P5 |
| P3 | 채널 매핑 | 매핑 버전 관리, 매핑 실패 -> OMS 보류, 한 채널 상품 -> 여러 SKU(세트) 표현 | 미정 |
| P4 | 세트 | SKU의 한 종류 / 별도 엔티티, 구성 변경 시 버전 | 미정 |
| P5 | 실측 값 | 신고값, 실측값 둘 다 보관 여부, 실측 반영 시 새 버전 여부, 오차 클 때 처리 | 미정 |
| P6 | 통관 정보 | HS 코드 6자리(국제 공통) / 국가별 10자리, 누락 시 OMS 보류 연결 | 미정 |
| P7 | 다른 시스템에 전달하는 방식 | 동기 조회 API + 캐시 / 이벤트 복제. 버전 불변 = `(sku_id, version)` 캐시 영구 유효 | 미정 |
| P8 | 취급 속성 범위 | v1 플래그만 / 로트, 유통기한까지(WMS와 맞물림) | 미정 |
