# 명령 전달의 정합성: outbox + api-client + 멱등 키

> OMS 쟁점 18 결정의 근거 문서. OMS가 WMS(이후 TMS 포함)에 보내는 **명령**(출고 요청 생성, 품목 제거, 가로채기, 주소 변경)에 적용한다. 이벤트(웨이브 릴리스, 출고 완료, 재고 변동)는 SQS + inbox로 느슨하게 받는다.

## 1. 지켜야 하는 것

> OMS DB에 "명령을 보낸다"가 커밋되었으면, WMS는 그 명령을 **정확히 한 번 처리한 것과 같은 결과**를 가져야 한다. 커밋되지 않았으면 WMS에는 아무 일도 없어야 한다.

네트워크와 프로세스는 언제든 끊긴다. 그래서 "정확히 한 번 전송"은 만들 수 없다. 대신 **적어도 한 번 전송 + 받는 쪽 중복 제거 = 결과적으로 한 번**을 만든다. 세 요소는 이 식의 각 항을 맡는다.

| 요소 | 맡는 것 | 보장 |
|---|---|---|
| outbox | 보낼 의도를 상태 변경과 같은 트랜잭션에 남김 | 커밋됐으면 반드시 언젠가 보낸다, 롤백됐으면 안 보낸다 |
| api-client | 커밋된 의도를 꺼내 HTTP로 보내고 응답을 받음, 실패하면 다시 보냄 | 적어도 한 번 전달 + 접수 / 거절을 즉시 앎 |
| 멱등 키 | 같은 명령이 두 번 와도 WMS가 한 번만 처리 | 재시도해도 결과가 하나 |

## 2. 하나라도 빠지면 생기는 일

### 2.1 outbox 없이 트랜잭션 안에서 API 호출

```text
OMS: BEGIN -> 출고 요청 저장 -> WMS API 호출(성공) -> COMMIT 실패(제약 위반, 커넥션 끊김)
결과: WMS는 출고 요청을 받아 피킹 시작, OMS에는 출고 요청이 없음 -> 유령 출고
```

DB 트랜잭션과 HTTP 호출은 하나로 묶을 수 없다(이중 쓰기 문제). 호출이 트랜잭션 안에 있으면 롤백이 WMS 쪽을 되돌리지 못한다. 덤으로 HTTP 대기 시간 동안 DB 락과 커넥션을 잡고 있다.

### 2.2 outbox 없이 커밋 후 바로 API 호출

```text
OMS: BEGIN -> 출고 요청 저장 -> COMMIT -> (여기서 프로세스 종료, 배포, OOM) -> 호출 안 됨
결과: OMS는 SENT 직전 상태로 영원히 대기, WMS는 모름 -> 주문 증발
```

커밋과 호출 사이 틈에서 죽으면 "보내야 한다"는 사실이 메모리에만 있었으므로 사라진다. outbox는 이 사실을 DB에 남겨 재시작 후에도 디스패처가 다시 꺼내게 한다.

### 2.3 api-client 대신 명령도 큐로만 보냄

```text
OMS -> SQS -> WMS: 재고 실물 부족으로 거절 -> 거절을 다시 이벤트로 보냄 -> OMS가 언제 올지 모르는 응답을 기다림
```

동작은 가능하지만 명령에는 **받았는지, 받아들였는지**가 바로 필요하다. 거절되면 다른 창고로 보상(18의 실패 세 갈래)해야 하고, 출차 마감(13)이 걸려 있어 기다릴 시간이 짧다. 큐만 쓰면 응답 상관관계, 응답 타임아웃을 따로 만들어야 한다. api-client는 동기 응답으로 이것을 바로 준다. 단, 웨이브 릴리스나 출고 완료처럼 **나중에 일어나는 사실**은 응답이 아니라 이벤트로 온다.

### 2.4 멱등 키 없이 재시도

```text
OMS -> WMS: 출고 요청 생성 -> WMS 처리 완료 -> 응답이 오는 중 네트워크 끊김 -> OMS는 타임아웃
OMS: 실패로 보고 재시도 -> WMS가 출고 요청을 하나 더 만듦 -> 같은 물건 두 번 출고
```

타임아웃은 "실패"가 아니라 **"모름"**이다. 상대가 처리했는지 알 수 없으니 다시 보내야 하는데, 그러려면 두 번 받아도 한 번만 처리되어야 한다. 멱등 키가 재시도를 안전하게 만든다.

### 2.5 api-client 여러 곳에서 직접 호출

호출하는 곳마다 멱등 키 조립, 타임아웃, 재시도 간격, 오류 분류가 달라진다. 한 곳이라도 키를 빼먹으면 2.4가 다시 생긴다. 명령 전송은 `WmsCommandClient` 한 곳으로 모은다.

## 3. 흐름

```text
[OMS 트랜잭션]
  업무 상태 변경(출고 요청 CREATED) + order_process 단계 갱신 + command_outbox INSERT
  COMMIT

[디스패처] (스케줄러, FOR UPDATE SKIP LOCKED)
  command_outbox에서 미전송 행을 꺼냄. 같은 출고 요청의 명령은 생성 순서대로 하나씩(생성보다 취소가 먼저 가지 않게)
  -> WmsCommandClient.send(명령, 멱등 키)
     ├ 접수(2xx)        -> outbox 완료, order_process 다음 단계 대기(timeout_at 설정)
     ├ 거절(업무 오류)   -> outbox 완료, order_process가 보상 시작(예약 해제, 다른 창고 재할당)
     └ 타임아웃, 5xx    -> outbox 그대로, retry_count + 1, 다음 시도 시각 = 지수 백오프
                         재시도 N회 초과 -> order_hold(사람 처리)

[WMS]
  멱등 키 테이블에 (키) UNIQUE + 처음 처리 결과 저장
  같은 키가 다시 오면 처리하지 않고 저장해 둔 결과를 그대로 응답
```

## 4. 멱등 키

| 명령 | 키 |
|---|---|
| 출고 요청 생성, 가로채기 등 출고 요청당 한 번 | `(fulfillment_order_id, 동작)` |
| 출고 요청당 여러 번 올 수 있는 것(취소) | `(fulfillment_order_id, CANCEL, cancel_request_id)` |

- `request_id`는 추적, 로그 상관관계용이고 멱등 판단에 쓰지 않는다. 재시도마다 바뀌어도 된다.
- **멱등은 받는 쪽이 키를 저장해야 성립한다.** WMS는 키별 처리 결과를 보관해야 하며(보관 기간은 OMS 재시도 최대 기간보다 길게), 이것은 WMS 설계 시 요구사항이 된다.

## 5. 이벤트는 왜 느슨해도 되나

이벤트는 "이미 일어난 사실"이라 받는 쪽이 거절할 수 없고, 보내는 쪽이 응답을 기다리지 않는다. 필요한 것은 두 가지뿐이다.

- 빠짐없이 받기: WMS도 outbox로 발행(적어도 한 번).
- 두 번 받아도 한 번 반영: OMS inbox `(source, message_id)` PK로 처리 트랜잭션 안에서 중복 제거. 재고 변동처럼 순서가 중요한 것은 순번(15의 `last_wms_seq`)으로 오래된 것을 버린다.

## 6. 남는 한계

- 디스패처가 밀리면 명령이 늦게 간다. 13의 "웨이브 직전 미전송" 경보가 이것을 잡는다.
- WMS 장애가 길면 재시도가 쌓인다. 백오프 상한과 N회 후 사람 처리로 끊는다.
- outbox 행은 완료 후 일정 기간 보관 뒤 삭제(파티션 또는 배치). 수치는 실험 단계에서.
